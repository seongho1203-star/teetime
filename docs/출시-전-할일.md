# 앱 출시 전 할 일

웹앱으로는 못 하고 **Capacitor로 감싸는 그 작업에서 같이 해야 하는 것들**을
모아 둔다.

지금은 웹앱(GitHub Pages)으로 돌고 있다.

**순서가 정해졌다 — 아이폰이 먼저다**(사용자가 정했다. 아래 0-3번).
남은 오류 셋이 전부 아이폰 것이라, 저장소 주인 폰에 진짜 앱으로 깔아
확인하는 것이 첫걸음이다. 애플 개발자 등록($99/년)을 하기로 했고,
**맥은 안 쓴다** — 클라우드 빌드가 대신한다.
안드로이드는 **$25 한 번**이라 급할 것이 없어 뒤로 미뤘다.

## 큰 순서 — **네이티브 일은 한꺼번에, 맨 마지막에** (사용자가 정했다)

사용자 판단이다 — `나머지 기능이나 오류 또는 기능 추가 완료후 제일
마지막에 그 작업을 하면 어때?` **그대로 한다.** 까닭이 분명하다:

**고치는 속도가 열 배 차이 난다.** 지금 껍데기는 웹 주소를 그대로 띄우므로
(0-3번) **밀면 폰에서 바로 보인다.** 앱 쪽(Swift)을 건드리는 순간 한 바퀴가
`빌드 → 올리기 → 애플이 처리 → 폰에서 갱신`으로 **30분**이 된다.
화면과 기능은 여러 번 고쳐 보며 다듬는 일이라, 그 속도를 마지막까지
쥐고 있는 것이 맞다.

그래서 일을 두 판으로 나눈다:

| | 무엇 | 어디를 고치나 | 한 바퀴 |
|---|---|---|---|
| **1판 (지금)** | 화면·기능·오류 전부 | 웹만 | **밀면 바로** |
| **2판 (마지막)** | 아래 네이티브 것들을 **한 번에** | 앱(Swift)까지 | 30분 |

**2판에 묶을 것 — 흩어 놓지 말 것:**

- ~~**입력칸을 네이티브로**(2-1번)~~ — **만들어 두었다**(2-1번 참고).
  사용자 요청(`댓글창이랑 채팅창 네이티브로 수정하자`)으로 2판을 기다리지
  않고 먼저 했다. **TestFlight로 새 판을 받아 깔아야 보인다** — 그전까지는
  예전 웹 글칸이 그대로 쓰인다(플러그인이 없으면 저절로 물러난다).
- ~~`server` 한 덩어리를 지워 **출시용으로 바꾸는 것**(0-3번)~~ —
  **했다**(사용자 요청 — `앱 출시용으로 진행해줘`). 아래 `0-4번`을 볼 것.
- ~~**`화면 판 …` 줄 걷어내기**~~ — **했다.** `ncStatus()` 줄도 함께 걷었고,
  그 자리는 이제 `앱제작: 악마제리` · `버전 1.0` 두 줄이다(사용자가 정한 문구).
- **알림을 FCM으로**(1번) — **아직이다. 지금 앱에는 알림이 아예 안 온다.**
  화면을 담았다고 달라지는 자리가 아니다(iOS 웹뷰에 웹푸시가 없다).
  **스토어에 올리기 전에 이것부터 할 것** — 아래 0-4번의 그 줄이다.
- **알림음 `까꿍`**(1번)과 **소리 두 번**(1-1번) — 위와 같은 자리다.
- **알림을 누르면 그 화면으로**(4번) — 아이폰에서 확실히.

## 0. 구글플레이에 올리기 — 미리 알아 둘 것

**기술보다 절차가 오래 걸린다.** 아래 셋은 코드와 상관없이 걸리는 시간이다.

| | 무엇 | 걸리는 것 |
|---|---|---|
| 등록비 | **$25**, 한 번만 | 즉시 |
| 테스트 | **12명이 14일 연속** 설치해 두어야 프로덕션 신청이 열린다 | **최소 2주** |
| 심사 | 올린 뒤 검토 | 보통 몇 시간~며칠 |

**12명 규칙이 제일 큰 벽이다.** 2023년 11월 13일 이후에 만든 **개인** 개발자
계정에 걸린다. 안드로이드 폰을 쓰는 사람 12명이 **각자 구글 계정으로 초대
링크를 눌러 실제로 설치**하고, 그 상태를 14일 **연속** 유지해야 한다.
**`내부 테스트`가 아니라 `비공개 테스트`여야 한다** — 아래 `12명은 어떻게
설치하나`를 볼 것.
에뮬레이터·중복 계정은 안 쳐 준다. 중간에 한 명이 지우면 그 사람 몫은 끊긴다.
→ **우리는 모임이 50~100명이라 이건 오히려 유리하다.** 안드로이드 쓰는 회원
열둘을 모으면 되고, 그 2주가 곧 실사용 시험이 된다.

**웹뷰만 감싼 앱은 반려된다**(정책 4.3 `최소 기능`). 2026년 들어 자동 심사가
더 깐깐해졌다. 우리는 **푸시 알림 · 알림음 · 뱃지 · 딥링크**가 붙는 진짜
앱이라 이 기준은 넘지만, **그 네이티브 기능들을 실제로 붙이고 나서 올려야
한다** — 껍데기만 먼저 올리면 그게 곧 반려 사유다.

### 올린 뒤에 바꿀 수 있는 것 / 없는 것

| 무엇 | 어떻게 |
|---|---|
| **웹 화면·기능**(우리가 늘 고치는 것) | 아래 참고 — **어느 길을 고르느냐에 달렸다** |
| 스토어 목록의 아이콘·스크린샷·설명 | Play Console에서 **바로**. 새 빌드 필요 없음 |
| **폰 홈 화면의 앱 아이콘** | 앱 파일 안에 있다 → **새 버전을 올려야 한다** |
| 앱 이름 | 스토어 이름은 바로, 홈 화면 이름은 새 버전 |
| **패키지 이름**(`com.kkakkung.app`) | **영영 못 바꾼다** |
| **서명 키** | 잃으면 **갱신을 영영 못 한다.** Play 앱 서명을 켜서 구글에 맡길 것 |

**기능 갱신은 두 갈래이고, 여기서 일하는 방식이 갈린다.**

1. **앱 안에 웹 파일을 넣는다**(Capacitor 기본, 심사에 안전)
   - 고칠 때마다 **PC에서 빌드해 새 버전을 올리고 심사를 기다린다.**
   - 지금처럼 "고쳐서 푸시하면 끝"이 아니게 된다 — **이게 제일 큰 변화다.**
   - 대신 사용자는 자동 업데이트로 조용히 받는다.
2. **앱은 껍데기만 두고 웹 주소를 띄운다**(`server.url`)
   - 지금처럼 **푸시만 하면 모두에게 바로** 반영된다. 빌드도 심사도 없다.
   - 대신 **정책 4.3에 걸릴 위험이 커진다** — 심사 눈에는 웹뷰 껍데기에
     가깝다. 알림 같은 네이티브 기능이 확실히 붙어 있어야 한다.

**섞는 길도 있다** — 웹 파일을 넣어 두고(1번) 급한 것만 원격으로 덮는 방식
(Capacitor Live Update). 유료 서비스이고 설정이 하나 더 는다.

### 아직 없는 것

- **개인정보처리방침 URL** — 없으면 콘솔에서 반려된다. 카카오 로그인으로
  이름·전화번호·차량번호를 받으므로 반드시 필요하다.
- **스토어 그래픽** — 아이콘 512×512는 있다(`public/icon-512.png`).
  **가로 배너 1024×500**과 **폰 스크린샷 2장 이상**은 아직 없다.
- **적응형 아이콘** — 안드로이드 홈 화면 아이콘은 앞/뒤 두 겹으로 만든다.
  `public/icon-maskable.png`(80%로 줄여 흰 바탕 가운데)가 그 앞장이 된다.

**사용자가 직접 짚어 둔 것 — 이 셋은 반드시 챙길 것:**

| | 무엇 | 지금 상태 |
|---|---|---|
| 1 | 알림음을 `까꿍`으로 | 앱을 **보고 있을 때만** 남. 알림으로 오는 소리는 폰 기본음 |
| 1-1 | 소리가 두 번 나는 것 | **안드로이드는 해결, 아이폰은 그대로** (실기기 확인) |
| 2 | 아이폰 대화창에서 키보드가 화면을 미는 것 | 웹으로는 넉 대를 헛짚었다. 못 고침 |
| 4 | 알림을 누르면 그 화면으로 | 웹으로 해 뒀다. **아이폰에서 안 되면 여기서 확실히** |

**웹에서 할 만큼 했고 남은 것은 네이티브 몫**이다. 감싸기 시작하면
이 파일부터 열 것. (3번은 사용자가 짚은 것이 아니라 있으면 좋은 것이다.)

## 0-1. 스토어 없이 APK만 뿌리는 길 (검토함 — 지금은 안 한다)

"APK로 만들어 각자 깔면 어떠냐"를 재 봤다. **위 0번의 절차(등록비 · 12명이
14일 · 심사)를 통째로 건너뛴다**는 게 이 길의 값이고, **PC도 필요 없다** —
GitHub Actions 러너에 안드로이드 SDK와 JDK가 이미 깔려 있어서, `android/`
폴더를 저장소에 넣고 워크플로가 `gradlew assembleRelease`를 돌려 Release에
APK를 붙이면 폰에서 링크만 눌러 받으면 된다.

**그런데 넷이 걸린다:**

1. **알림이 오히려 죽는다.** Capacitor가 쓰는 안드로이드 웹뷰에는
   **웹푸시(Push API · Notification)가 없다.** 지금 알림은 서비스워커
   웹푸시라, 껍데기만 만들면 **홈 화면에 추가해 쓸 때는 오던 알림이
   앱에서는 안 온다.** 살리려면 FCM으로 옮겨야 하고(위 '함께 정해 둔 것들'),
   **그게 이 일의 대부분이다.**
   - 예외는 **TWA**다. 그건 크롬이 화면을 그리는 껍데기라 지금 알림이
     그대로 산다. 대신 알림음은 못 바꾸고(폰 기본음), 주소 확인용
     `assetlinks.json`을 도메인 뿌리에 올릴 저장소가 하나 더 필요하다.
2. **자동 갱신이 없다.** 앱 안에 웹 파일을 넣는 방식이면 고칠 때마다
   100명이 새 APK를 다시 깔아야 한다. `server.url`(껍데기가 웹 주소를
   띄우는 방식)로 두면 이 문제가 없다 — **사이드로딩에는 정책 4.3 심사가
   없으니 껍데기여도 상관없다.** 스토어에 낼 때만 문제가 된다.
3. **설치 문턱.** `알 수 없는 앱 설치 허용`을 켜야 하고, Play Protect가
   `안전하지 않을 수 있다`를 띄운다. 100명에게 한 명씩 안내할 일이다.
4. **아이폰은 아예 안 된다.** APK는 안드로이드 전용이라 안내가 두 벌이 된다.

**얻는 것을 세어 보면 사실상 `까꿍` 알림음 하나다.** 알림 · 뱃지 · 알림
누르면 이동은 안드로이드에서 **이미 홈 화면 추가로 되고 있고**, 2번(아이폰
키보드)은 APK와 상관이 없다.

**서명 키는 사이드로딩이어도 처음부터 릴리스 키로 만들 것.** 디버그 키로
뿌리면 나중에 스토어 키와 달라 덮어 설치가 안 되고, **회원 100명이 앱을
지웠다 다시 깔아야 한다.**

**결론 — 스토어에 갈 때 어차피 만들 껍데기라, APK만 따로 만들 이유가
지금은 없다.** 급해지면(알림음이 꼭 필요해지면) 위 순서로 하면 된다.

## 0-2. 출시 말고 **확인만** 해 보려면 (사용자 질문 — `어플 설치한 것처럼 확인할 방법 없어?`)

**웹으로 할 수 있는 '앱처럼'은 `홈 화면에 추가`가 끝이다.** 지금 남은
오류(아이폰 키보드 밀림 · 소리 두 번 · 천지인 깜빡임)는 그 위, 진짜 앱에서만
확인된다.

**핵심은 남은 오류가 전부 아이폰 것이라는 점이다.** 안드로이드는 공짜로
지금 바로 만들 수 있지만(아래), **셋 다 안드로이드에서는 원래 안 나므로
확인해 봐야 답이 안 나온다.** 여기서 길이 갈린다.

| | 확인 가능 | 드는 것 | 남은 오류에 답이 되나 |
|---|---|---|---|
| 안드로이드 APK | 지금 바로. PC도 필요 없다(GitHub Actions) | **공짜** | ❌ (셋 다 아이폰 것) |
| 아이폰 — 애플 개발자 | 맥 없이 클라우드 빌드 + TestFlight | **$99/년** | ✅ |
| 아이폰 — 맥 있는 사람 | Xcode 무료 프로비저닝 | **공짜, 다만 7일마다 다시** | ✅ |

→ **사용자가 두 번째(애플 개발자 $99/년)로 정했다. 아래 0-3번이 그 순서다.**
계정이 앱마다가 아니라 사람마다 하나라, 나중에 다른 앱을 만들 때도 그대로
쓴다는 것이 결정적이었다.

**맥이 있는 회원이 있으면 그게 제일 싸다.** Xcode의 무료 프로비저닝은
개발자 등록 없이 제 아이폰에 깔 수 있다 — 7일이면 만료되지만 **확인용으로는
그걸로 충분하다.** 없으면 $99/년이 유일한 길이다(맥은 없어도 된다 —
Codemagic 같은 클라우드 빌드가 맥을 대신한다).

### 확인용 껍데기는 출시용과 다르다 — 훨씬 작다

**둘 다 폰에 깔리는 진짜 앱이다**(사용자 질문 — `껍데기를 만든다했는데
실제 설치되는 앱하고 다른거야?`). 아이콘도 전체화면도 같고 **보이는 것이
한 픽셀도 안 다르다.** 갈리는 것은 **화면을 어디서 가져오느냐** 하나이고,
거기서 `고치는 속도` · `인터넷이 끊겼을 때` · `스토어 심사`가 따라온다.
**고치려는 오류는 둘 다 똑같이 난다** — 키보드 밀림도 천지인 깜빡임도
화면을 담는 그릇(WKWebView)이 만드는 것이라 화면의 출처와 무관하다.
확인이 끝나면 **같은 앱의 설정을 바꿔 다시 올리면** 출시용이 된다
(새로 만드는 것이 아니라 폰에서는 앱 갱신으로 넘어간다).


**`server.url`로 지금 웹 주소를 그대로 띄우는 껍데기**면 된다. 화면 코드를
한 줄도 안 옮겨도 되고, 그것만으로 위 셋의 답이 나온다:

- **키보드 밀림** — `@capacitor/keyboard`의 `resize: 'native'` 하나로 갈린다.
- **소리 두 번** — 앱이 앞에 있을 때 알림을 어떻게 띄울지 앱이 정한다.
- **천지인 깜빡임** — 감싸도 그대로일 것이라 본다(2-1번). **그걸 확인하는
  것 자체가 값이다** — 지금은 짐작이고, 확인되면 입력칸을 네이티브로 바꿀지
  판단할 근거가 생긴다.

**대신 껍데기에서는 두 가지가 안 된다. 미리 알고 시작할 것:**

1. **알림이 안 온다.** iOS 웹뷰에는 웹푸시가 없다(0-1번 1항과 같은 자리).
   확인용이라 상관없지만, **알림까지 보려면 FCM 옮기기가 따로 필요하다.**
2. **카카오 로그인이 막힐 수 있다.** 카카오는 앱 안 웹뷰에서의 로그인을
   막는다 — **여기가 제일 잘 걸리는 자리다**(아래 '함께 정해 둔 것들'의
   딥링크 항목). `@capacitor/browser`로 바깥 브라우저를 띄우고 커스텀
   스킴으로 돌아오게 해야 하고, 카카오와 Supabase 양쪽 콘솔에 그 주소를
   등록해야 한다. **확인용 껍데기의 품은 사실상 이것 하나다.**

**안드로이드 APK 쪽은 0-1번에 이미 재 두었다** — 거기 결론(`지금은 안 한다`)은
**뿌리는 것**에 대한 판단이고, **확인**은 다른 이야기다. 다만 위 표대로
아이폰 오류에는 답이 안 되므로, 안드로이드에서만 나는 것이 새로 나왔을 때
꺼내 쓸 것.

## 0-3. 정해진 길 — 애플 개발자 등록 → 내 폰에 설치 (**끝났다**)

> 여덟 걸음이 다 끝나 **앱이 폰에 깔렸다.** 아래 표의 확인 결과는
> 2번(키보드 밀림 ✅ 고쳐짐) · 2-1번(천지인 깜빡임 ❌ 그대로, 예고한 대로)
> 각 꼭지에 적어 두었다. 소리 두 번(1-1)은 알림이 안 오는 껍데기라
> 아직 확인 못 했다.

**사용자가 정했다** — `앱으로 출시못하더라도 다른 앱개발해서 등록할수도
있으니 앱개발자 등록하자. 그래서 내폰에 직접 설치하고 오류를 수정하고싶어.`

계정은 **앱마다가 아니라 사람마다** 하나이므로, $99로 1년간 앱을 몇 개
만들든 다 쓴다. 그것이 위 표에서 `맥 있는 사람`(공짜지만 7일마다 다시)을
제치고 이 길로 온 까닭이다.

### 사용자가 손으로 할 일 (등록)

**아이폰의 `Apple Developer` 앱으로 하는 것이 제일 쉽다** — 신분 확인을
카메라로 그 자리에서 한다. PC로 하면 서류를 따로 올려야 한다.

1. 앱스토어에서 `Apple Developer` 앱 설치
2. 쓰던 Apple ID로 로그인 (**2단계 인증이 켜져 있어야 한다**)
3. `Account` → `Enroll`
4. `Individual / Sole Proprietor`(개인) 선택
   → **앱스토어에 실명이 개발자 이름으로 뜬다.** 회사 이름으로 하려면
   사업자 등록이 필요한 `Organization`이라 절차가 훨씬 길다.
5. 이름·주소·전화번호를 **영문**으로, 신분증 촬영
6. $99 결제 (해외 결제 되는 카드. 매년 자동 갱신)
7. **승인까지 하루~이틀.** 메일이 온다.

### 승인된 뒤 — 이쪽에서 할 일 (**끝났다**)

**확인용 껍데기부터 만든다**(위 0-2번의 그 껍데기). 웹 파일을 앱 안에
넣지 않고 `server.url`로 지금 주소를 띄우는 방식이다.

**이 선택의 이유는 고치는 속도 하나다.** 웹 파일을 넣으면 한 줄 고칠
때마다 `빌드 → TestFlight 올리기 → 애플이 처리 → 폰에서 갱신`이라 한
바퀴에 한 시간이 넘는다. 키보드 밀림처럼 **여러 번 고쳐 보며 잡아야
하는 것**을 그 속도로는 못 잡는다. `server.url`이면 지금처럼 밀기만
하면 폰에서 다시 열어 바로 본다.

| | 할 일 | 누가 | 상태 |
|---|---|---|---|
| 1 | Capacitor 붙이기 (`capacitor.config.ts` · `ios/`) | 이쪽 | ✅ |
| 2 | `@capacitor/keyboard`를 `resize: 'native'`로 (2번 항목의 그 한 줄) | 이쪽 | ✅ |
| 3 | 카카오 로그인을 바깥 브라우저로 빼기 (`@capacitor/browser` + 커스텀 스킴) | 이쪽 | ✅ |
| 4 | **Supabase**에 그 주소 등록 (카카오 콘솔은 안 건드린다 — 아래) | **사용자** | ✅ |
| 5 | App Store Connect에서 앱 만들고 API 키 발급 | **사용자** | ✅ |
| 6 | 그 키를 GitHub Secrets에 넣기 | **사용자** | ✅ |
| 7 | macOS 러너로 빌드해 TestFlight에 올리는 워크플로 | 이쪽 | ✅ |
| 8 | 폰에 TestFlight 깔고 설치 | **사용자** | ✅ |

- **맥은 안 산다.** 이 저장소가 공개라 **GitHub Actions의 macOS 러너가
  공짜**다 — 거기서 빌드해 TestFlight로 올린다(`.github/workflows/ios.yml`).
  인증서도 손으로 안 만든다: `xcodebuild -allowProvisioningUpdates`가
  App Store Connect API 키로 **스스로 만들어 받는다.**
- **제일 잘 막히는 자리는 3·4번(카카오 로그인)이다.** 카카오는 앱 안
  웹뷰에서의 로그인을 막으므로, 이걸 안 하면 **껍데기에서 로그인 자체가
  안 되어 아무것도 확인 못 한다.** 위 0-2번에서 `확인용 껍데기의 품은
  사실상 이것 하나다`라고 적어 둔 것이 이 줄이다.
  - 앱에서는 `signInWithKakao()`가 **웹뷰를 안 옮기고**(`skipBrowserRedirect`)
    주소만 받아 `@capacitor/browser`로 연다 — 아이폰에서 사파리 창으로 떠서
    카카오가 정상 브라우저로 봐 준다. 끝나면 `kkakkung://auth`로 앱을 다시
    부르고 `lib/native.ts`가 받아 세션을 세운다.
  - **카카오 콘솔은 안 건드려도 된다.** 카카오가 보는 것은 늘 Supabase의
    콜백 주소 하나뿐이고, 커스텀 스킴은 그 **뒤에** Supabase가 우리를 부를
    때만 쓰인다. 그래서 등록할 곳은 **Supabase 한 곳**이다.
  - 받는 쪽은 **물음표(`?code=`)와 우물정자(`#access_token=`)를 둘 다 본다** —
    지금은 PKCE라 앞엣것으로 오지만, 설정이 바뀌면 뒤엣것으로 온다.
    한쪽만 보면 그때 **조용히** 로그인이 안 된다.
  - **앱이 꺼져 있다 그 주소로 켜지는 경우** `appUrlOpen`이 안 온다.
    그래서 켜질 때 `App.getLaunchUrl()`을 한 번 더 본다.
- **알림은 이 껍데기에서 안 온다**(iOS 웹뷰에 웹푸시가 없다). 그래서
  `소리 두 번`(1-1번)은 이 단계에서 확인이 안 되고, FCM으로 옮긴 뒤에야
  답이 나온다. **셋 중 둘만 이번에 잡힌다:**

| | 이 껍데기로 | 왜 |
|---|---|---|
| 키보드 밀림 (2번) | ✅ 고쳐진다 | `resize: 'native'` 한 줄 |
| 천지인 깜빡임 (2-1번) | ✅ **확인**된다 | 고쳐지진 않는다. 그래도 입력칸을 네이티브로 바꿀지 판단할 근거가 생긴다 |
| 소리 두 번 (1-1번) | ❌ 나중에 | 알림이 안 오므로 볼 것이 없다 |

- **TestFlight 빌드는 90일이면 만료된다.** 다시 올리면 그만이지만,
  회원들에게 뿌리는 길로 쓰지는 말 것 — 90일마다 100명이 다시 깔아야 한다.
  뿌리는 것은 스토어 출시(0번) 몫이다.
- **`내부 테스터`는 심사를 안 받는다.** 처음에 `첫 빌드는 하루쯤 기다린다`고
  알렸는데 그건 **외부 테스터** 이야기였다 — 제 계정에 제가 테스터로 들어가는
  `내부 테스터`(최대 100명)는 심사 없이 **처리(10~30분)만 끝나면 바로 깔린다.**
  회원들에게 나눠 줄 때도 그 100명 안이면 그대로 된다.
- **패키지 이름은 정해졌다 — `com.kkakkung.app`. 이제 못 바꾼다.**
  (앱이 App Store Connect에 만들어지기 전까지는 `capacitor.config.ts`
  한 줄이지만, 만든 뒤에는 바꾸면 다른 앱이 된다.)

### 사용자가 손으로 할 일 — 네 걸음

**1. Supabase에 돌아올 주소 등록** (제일 중요하다. 이게 없으면 로그인이 막힌다)

`supabase.com` → 이 프로젝트 → `Authentication` → `URL Configuration` →
`Redirect URLs`의 `Add URL` → **`kkakkung://auth`** → 저장.

**2. 애플에 앱 자리 만들기**

- `developer.apple.com` → `Certificates, Identifiers & Profiles` →
  `Identifiers` → `+` → `App IDs` → `App` →
  Description `Kkakkung`, Bundle ID는 **Explicit**으로 `com.kkakkung.app` → `Register`
- `appstoreconnect.apple.com` → `앱` → `+` → `신규 앱`
  → 플랫폼 `iOS` · 이름 `까꿍` · 기본 언어 `한국어` · 번들 ID `com.kkakkung.app`
  · SKU는 아무거나(`kkakkung`)

**3. 열쇠 넷을 만들어 GitHub에 넣기**

- `appstoreconnect.apple.com` → `사용자 및 액세스` → `통합` → `팀 키` →
  `+` → 이름 아무거나 · 액세스 **`App 관리자`** → 생성
  → **`.p8` 파일은 그때 한 번만 받을 수 있다.** 꼭 저장할 것
  → 같은 화면의 `키 ID`와 `발급자 ID`를 적어 둔다
- `developer.apple.com` → `Membership details`의 **`Team ID`**(열 자리)
- 저장소 → `Settings` → `Secrets and variables` → `Actions` →
  `New repository secret`으로 넷을 넣는다:

| 이름 | 값 |
|---|---|
| `APPSTORE_KEY_ID` | 키 ID |
| `APPSTORE_ISSUER_ID` | 발급자 ID |
| `APPSTORE_KEY_P8` | `.p8` 파일을 **메모장으로 열어 통째로** 붙여넣기 |
| `APPLE_TEAM_ID` | Team ID |

**4. 빌드 돌리고 폰에 깔기**

- 저장소 → `Actions` → `아이폰 앱 (TestFlight)` → `Run workflow`
- 20분쯤 뒤 `appstoreconnect.apple.com` → `까꿍` → `TestFlight`에 뜬다
- 같은 화면의 `내부 테스트`에 **본인을 테스터로 추가**
- 폰에 앱스토어에서 **`TestFlight`** 앱을 깔고 열면 `까꿍`이 보인다

## 0-4. 출시용으로 바꿨다 — 화면이 앱 안에 담긴다

사용자 요청 — `앱 출시용으로 진행해줘`. `capacitor.config.ts`에서
**`server` 한 덩어리를 지웠다.** 이제 `npm run build`가 만든 `dist`가
앱 안에 담긴다(이모티콘 그림까지 함께).

**앱을 새로 만든 것이 아니다** — 같은 앱(`com.kkakkung.app`)의 새 판이라
폰에서는 앱 갱신으로 조용히 넘어간다.

### 무엇이 달라졌나

| | 껍데기이던 때 | 지금 |
|---|---|---|
| 화면을 어디서 | GitHub Pages에서 받아 옴 | **앱 안에 담김** |
| 웹만 고치면 | 밀면 폰에서 바로 | **앱을 새로 깔아야 보임 (한 바퀴 30분)** |
| 인터넷이 끊기면 | 흰 화면 | 화면은 뜸(자료만 안 옴) |
| 이모티콘 그림 | 밖에서 받아 옴 | 앱 안에 있음 — 빠르고 통신량 0 |
| 알림 | **안 옴** | **그대로 안 옴** (아래) |

**되돌리는 길은 한 줄이다.** 화면을 여러 번 고쳐 보며 다듬어야 하는 일이
생기면 `capacitor.config.ts`에 그 한 줄을 도로 붙이면 그 동안만 껍데기가
된다(지운 자리에 주석으로 남겨 두었다).

```ts
server: { url: 'https://seongho1203-star.github.io/teetime/' },
```

**웹은 그대로 돈다.** 홈 화면에 추가해 쓰던 회원은 예전과 똑같다 —
앱은 그 위에 하나 더 생기는 길이다.

### 확인한 것

`dist`를 **루트로 띄워** 열어 봤다(`cd dist && python3 -m http.server`) —
앱에서는 문서가 `capacitor://localhost/index.html`에 있으므로 그것과 같은
자리다. 로그인 화면이 뜨고 · 이모티콘이 200으로 풀리고 · 404도 자바스크립트
오류도 0이었다. **`vite.config.ts`의 `base: './'`가 그 자리를 막고 있는
것**이라, 그 줄을 건드리면 앱이 통째로 흰 화면이 된다.

### 스토어에 올리기 전에 남은 것

**지금 이대로 심사에 넣지 말 것.** 둘이 걸린다.

1. ~~**알림이 안 온다(1번).**~~ — **붙였다**(사용자 요청 —
   `FCM으로 옮겨서 앱에서도 알림받을수있게해줘`). 아래 `0-5번`을 볼 것.
   **다만 사용자가 애플 열쇠(.p8) 하나를 만들어 넣어야 켜진다**
   (`docs/설치.md` 7-1번).
2. **애플 4.2 (최소 기능).** 웹뷰만 감싼 앱은 반려된다. 우리는 네이티브
   글칸이 있고 푸시까지 붙이면 넘지만, **푸시 없이 먼저 올리면 그게 곧
   반려 사유다.**

**사용자가 손으로 할 일(스토어 제출)은 그다음이다** — 앱 아이콘·스크린샷·
설명·연령 등급·**개인정보 처리방침 주소**(필수, 웹페이지 하나면 된다)를
App Store Connect에 채우고 심사에 넣는다.
**그 절차와 먼저 막아야 할 반려 사유 셋은 아래 `0-7번`에 있다.**

**그때까지는 TestFlight로 쓴다.** 내부 테스터는 심사가 없고 100명까지
되므로, 모임이 50~100명이면 그 안에서 그대로 나눠 줄 수 있다 —
다만 **빌드가 90일이면 만료된다**(0-3번 참고).

## 0-5. 앱에서도 알림을 받는다 — **애플에 바로 민다**

사용자 요청 — `FCM으로 옮겨서 앱에서도 알림받을수있게해줘`.

**FCM을 안 썼다. 그 까닭이 이 꼭지의 핵심이다.** 지금 내는 것이
아이폰뿐인데, 파이어베이스를 끼우면 사용자가 할 일이 다섯으로 는다 —
프로젝트 만들기 · 앱 등록 · `GoogleService-Info.plist` 넣기 · APNs 키를
파이어베이스에 올리기 · 발송기에 서비스 계정 JSON(수십 줄짜리 비밀값)
넣기. **애플에 바로 보내면 그게 `.p8` 열쇠 하나가 된다.** 사용자는 폰으로
일하므로 손이 적은 쪽이 맞다.

**안드로이드를 낼 때 FCM을 더한다.** `@capacitor/push-notifications`는
그때 FCM 토큰을 주고, 받는 쪽 짜임(표 · 고르는 규칙 · 죽은 토큰 걷기)은
그대로 쓴다. 발송기에 갈래를 하나 더 붙이면 된다.

### 무엇이 붙었나

| | 어디 |
|---|---|
| 권한 · 등록 · 토큰 저장 · 알림 누르기 | `src/lib/native-push.ts` |
| 앱이면 그쪽으로 넘기기 | `src/lib/push.ts` (화면은 안 고쳤다) |
| 애플로 밀기(.p8 → ES256 JWT) | `supabase/functions/notify/index.ts` |
| 등록 답을 플러그인에 넘기기 | `ios/App/App/AppDelegate.swift` |
| 알림 권한 | `ios/App/App/App.entitlements` |

- **표를 새로 안 만들었다.** 웹 구독이 쓰던 `push_subscriptions`에
  `endpoint`를 `apns:<토큰>`으로 넣는다 — 붙여넣을 SQL이 없고, 받는 사람을
  고르는 규칙(`only`·`except`·대화 스위치)과 죽은 구독을 걷는 자리가
  **웹과 한 코드로** 남는다.
- **앱을 보고 있을 때는 알림을 안 띄운다**(`presentationOptions: []`) —
  아래 1-1번(소리 두 번)이 앱에서는 이걸로 끝난다.
- **아카이브를 서명 없이 만드는 것과 부딪혔다.** 서명을 끄면 Xcode가
  `entitlements` 처리도 건너뛰어 알림 권한이 앱에 안 실린다 — 빌드는
  초록이고 TestFlight에도 올라가는데 **폰에서 등록만 조용히 거절당한다.**
  그래서 `ios.yml`이 `archived-expanded-entitlements.xcent`를 직접 넣고,
  **들어갔는지 확인하고 넘어간다.**

### 아직 확인 안 된 것

**애플에 진짜로 닿는지는 실기기에서만 알 수 있다.** 여기서 확인한 것은
열쇠 읽기와 서명(ES256)이 맞다는 것까지다 — 그건 실제로 돌려 검증했다.

안 오면 **Edge Functions → Logs**에 `apns <코드>`가 찍힌다:

| 코드 | 뜻 |
|---|---|
| `403` | 열쇠·Key ID·Team ID 중 하나가 어긋났다 |
| `400 TopicDisallowed` | 그 키가 이 앱(`com.kkakkung.app`)의 것이 아니다 |
| `400 BadDeviceToken` | 토큰이 못 쓰게 됐다(그 행은 저절로 걷힌다) |
| 아무것도 안 찍힘 | 비밀값 셋이 아직 없다 → 앱 기기를 건너뛴 것이다 |

폰 쪽에서 `내 정보 → 이 기기로 받기`를 켰는데 **`애플에서 답이 없습니다`**
가 뜨면 앱에 알림 권한이 안 실린 것이다(위 아카이브 자리).

## 0-6. 안드로이드까지 낸다 — 지금까지 붙인 것과 남은 것

사용자 요청 — `안드로이드까지 출시할거야`.

**코드 쪽은 다 붙였다.** `android/` 뼈대 · 알림(FCM) · 빌드 워크플로.
남은 것은 **돈과 시간이 드는 절차**이고, 그건 위 `0번`에 적어 둔 그대로다.

### 붙인 것

| | 어디 |
|---|---|
| 앱 뼈대(카카오 스킴 · 알림 권한 · 아이콘 · 첫 화면) | `android/` |
| 알림 받기(FCM 토큰) | `src/lib/native-push.ts` — 아이폰과 **같은 코드**, 표시만 `fcm:` |
| 알림 보내기 | `supabase/functions/notify` — `fcm:` 갈래 |
| 앱 만들기 | `.github/workflows/android.yml` |

- **맥이 필요 없다.** 우분투에서 그대로 돈다 — 아이폰 쪽보다 빠르고 싸다.
- **서명 열쇠가 없어도 만들어진다.** 등록비를 내기 전에도 **앱이 제대로
  만들어지는지** 확인할 수 있게 그렇게 두었다.

### 사용자가 손으로 할 일 — 순서대로

**1번을 제일 먼저 할 것.** 12명이 14일을 채워야 하는 시계가 그때부터
돌기 시작한다(위 0번). 나머지는 그 2주 안에 하면 된다.

1. **Play Console 등록 — $25, 한 번만.** <https://play.google.com/console>
   → 개발자 계정 만들기 → 결제
2. **앱 만들기** — Console에서 `앱 만들기`, 이름 `까꿍데이`(스토어에 뜨는
   이름. 앱 안 이름은 `까꿍` 그대로다)
3. **서명 열쇠(업로드 키)** — 아래 `열쇠 만들기`를 볼 것
4. **파이어베이스**(알림) — `docs/설치.md` 7-2번
5. **비공개 테스트에 12명 초대** → 각자 설치 → **14일 연속 유지**
   (아래 `12명은 어떻게 설치하나`를 볼 것)
6. **개인정보 처리방침 주소** — 없으면 콘솔에서 반려된다. 카카오 로그인으로
   이름·전화번호·차량번호를 받으므로 반드시 필요하다(웹페이지 하나면 된다)
7. **스토어 그래픽** — 아이콘 512×512는 있다(`public/icon-512.png`).
   **가로 배너 1024×500**과 **폰 스크린샷 2장 이상**은 아직 없다

### 열쇠 만들기 — **폰만으로는 안 되는 유일한 자리다**

앱에 서명할 열쇠(`.jks`)는 컴퓨터에서 `keytool`로 만든다.
**사용자가 컴퓨터에서 직접 만드는 쪽으로 정했다**(대화창에 열쇠가 남지
않는 길이다). 아래를 **컴퓨터 터미널에 통째로** 붙여넣으면 된다 —
`바꿀비밀번호`만 아무 글자로 고쳐서.

`keytool`은 자바에 딸려 온다. 없으면 <https://adoptium.net> 에서 받거나
Android Studio를 깔면 함께 들어온다.

```bash
# 1. 열쇠 만들기 (27년짜리)
keytool -genkeypair -v \
  -keystore upload.jks -alias upload \
  -keyalg RSA -keysize 2048 -validity 10000 \
  -storepass '바꿀비밀번호' -keypass '바꿀비밀번호' \
  -dname 'CN=kkakkung, O=kkakkung, C=KR'

# 2. GitHub 비밀값에 넣을 글자로 바꾸기 → upload.txt 에 담긴다
base64 -w0 upload.jks > upload.txt 2>/dev/null || base64 -i upload.jks | tr -d '\n' > upload.txt
echo '완료 — upload.txt 를 열어 통째로 복사하세요'
```

- 윈도우는 PowerShell에서 2번만 다르다:
  `[Convert]::ToBase64String([IO.File]::ReadAllBytes("upload.jks")) | Set-Content upload.txt`
- **`upload.jks`와 비밀번호는 잘 보관할 것.** 아래 `Play 앱 서명`을 켜면
  잃어버려도 재설정을 신청할 수 있지만, 안 켜면 갱신을 영영 못 한다.

만들었으면 GitHub → **Settings → Secrets and variables → Actions** 에 넷:

| 이름 | 값 |
|---|---|
| `ANDROID_KEYSTORE_B64` | `.jks` 파일을 base64로 바꾼 글자 |
| `ANDROID_KEYSTORE_PASSWORD` | 만들 때 정한 비밀번호 |
| `ANDROID_KEY_ALIAS` | 만들 때 정한 별칭(`upload`) |
| `ANDROID_KEY_PASSWORD` | 키 비밀번호(대개 위와 같게 둔다) |

**Play 앱 서명을 반드시 켤 것.** 그러면 진짜 서명 키는 구글이 보관하고
우리 것은 **업로드 키**가 된다 — **잃어버려도 구글에 재설정을 신청할 수
있다.** 안 켜면 열쇠를 잃는 순간 **갱신을 영영 못 한다.**

### 12명은 어떻게 설치하나 (사용자 질문 — `그12명은 어떻게 설치해?`)

**앱 파일을 나눠 주는 게 아니다.** 초대받은 사람은 **플레이스토어에서
평소처럼 받는다** — 다만 그 앱이 초대받은 사람 눈에만 보일 뿐이다.

**`내부 테스트`가 아니라 `비공개 테스트`(closed testing)여야 한다.**
내부 테스트는 바로 되고 편하지만 **12명·14일에 안 쳐 준다.** 여기서
길을 잘못 들면 2주를 통째로 다시 세게 된다.

1. **테스터 이메일을 모은다.** 안드로이드 폰을 쓰는 회원에게 **그 폰에
   들어가 있는 구글 계정(gmail 주소)**을 받는다.
   - **아이폰 쓰는 분은 못 도와준다.** 안드로이드만 센다.
   - **12명이 아니라 15명쯤 모을 것.** 한 명이라도 빠지면 열둘이 깨져
     날짜가 다시 시작된다.
   - 이메일을 **구글 그룹**(<https://groups.google.com>)에 모아 두면
     그 뒤로 사람을 넣고 뺄 때 Play Console을 안 건드려도 된다.
2. **Play Console → 테스트 → 비공개 테스트** 에서 트랙을 만들고,
   그 이메일 목록(또는 그룹 주소)을 테스터로 넣는다.
3. **AAB를 올려 출시한다.** 심사가 한 번 돈다(대개 몇 시간).
4. 그 화면에 뜨는 **초대 링크**를 회원들에게 보낸다
   (`https://play.google.com/apps/testing/com.kkakkung.app` 모양이다).
5. 회원은 **안드로이드 폰에서** 그 링크를 열고
   → `테스터 되기` → `Google Play에서 다운로드` → 평소처럼 설치.
   - **1번에서 적어 낸 그 구글 계정으로 로그인돼 있어야 한다.** 폰에
     계정이 여럿이면 엉뚱한 계정으로 눌러 "찾을 수 없음"이 뜬다.
6. **14일 동안 그대로 둔다.** 앱을 지우거나 `테스터 그만두기`를 누르면
   그 사람 몫이 끊긴다. 열둘 아래로 내려가면 날짜가 다시 시작된다.

**우리 모임에는 오히려 유리하다** — 50~100명이라 안드로이드 쓰는 회원
열둘은 쉽게 모이고, **그 2주가 곧 실사용 시험이 된다.**

**아이폰은 이 규칙이 없다.** TestFlight로 바로 나눠 줄 수 있고, 지금도
그렇게 쓰고 있다.

### Play에 올리는 것은 아직 손으로 한다

워크플로가 결과물(`kkakkung-aab`)만 남긴다. **첫 판은 어차피 손으로
올려야** Play에 앱이 만들어지고, 그다음부터 저절로 올리는 단계를 붙이면
된다(서비스 계정 열쇠가 하나 더 필요하다). 있지도 않은 것을 부르는
단계를 미리 넣어 두면 **돌릴 때마다 빨갛게 실패한다** — 그래서 안 넣었다.

## 0-7. 아이폰 앱스토어에 올리기 (사용자 질문 — `아이폰 같은 경우는 바로 애플스토어에 등록할수있어?`)

**된다 — 애플에는 구글의 `12명·14일`이 없다.** 만들어 둔 앱을 그대로
심사에 넣으면 되고, 결과는 보통 **하루~사흘**에 온다. 개발자 등록도
TestFlight도 이미 끝나 있으므로 **남은 것은 제출뿐이다.**

**반려될 자리가 셋 있었다.** 사용자가 `셋다 다해줘`라고 정해 **둘은
만들었고**, 남은 하나는 사람이 계정을 만들어 두는 일이다.
안드로이드에도 똑같이 걸리는 것이라 **어차피 해야 하는 것들이었다.**

### 먼저 막아야 할 셋

1. ~~**회원 탈퇴가 없다**~~ — **만들었다**(`내 정보 → 회원 탈퇴`).
   심사 규정 5.1.1(v)는 **계정을 만드는 앱은 앱 안에서 그 계정을 지울 수
   있어야 한다**고 못박아 두었고(2022년부터), 자동 검사에도 걸린다.
   **가장 확실했던 반려 사유다.**
   - 지우는 일은 DB의 `delete_me()`가 한다 — `auth.users` 한 줄을 지우면
     프로필·신청·표·정산 몫·알림 구독이 딸려 간다. 화면은 **DB가 못 하는
     둘**만 한다(이 기기 알림 끊기 · 저장소의 사진 파일 지우기).
   - **`추방(banned)`과 다른 일이다** — 그건 남이 막는 것이고 **행을 남겨
     두는 것이 곧 막는 방법**이다(위 '가입은 운영진 승인제' 참고).
     탈퇴는 본인이 지우는 것이라 **다시 로그인하면 새 가입 신청**이 된다.
   - **대화 글은 남는다**(`on delete set null`). 남의 대화가 중간중간 비면
     읽을 수 없게 된다 — 카톡에서 나간 사람 말이 남는 것과 같다.
2. ~~**`Apple로 로그인`이 없다**(4.8)~~ — **붙였다.** 카카오 같은 **남의
   로그인만** 쓰는 앱에는 맞먹는 로그인을 하나 더 내놓으라고 요구한다.
   규정 글에 카카오가 이름으로 적혀 있지는 않지만 **한국 앱이 이걸로
   반려된 사례가 많아** 미리 넣었다.
   - **사용자가 등록을 해야 살아난다** — `docs/설치.md` **3-3번**.
     그 전까지는 단추가 보이지만 누르면 오류가 난다.
   - **애플은 이름을 맨 처음 한 번만 준다.** 그 한 번을 놓치면 되받을 길이
     없어 **애초에 안 받고** 로그인 뒤에 닉네임을 한 번 묻는다.
3. **심사자가 앱 안으로 못 들어간다** — **이것만 사람이 할 일로 남았다.**
   우리 앱은 **로그인 + 운영진 승인**을 지나야 아무것도 안 보인다.
   심사자는 외국에 있고 우리 모임 사람이 아니라, 그냥 넣으면
   `승인 대기중` 화면만 보고 반려한다.
   - **계정을 하나 새로 만들어**(카카오도 되고 Apple도 된다) 앱에 한 번
     로그인시키고, 운영자가 그 사람을 **미리 승인해 둔다.** 그
     아이디·비밀번호를 App Store Connect의
     **`심사 정보 → 로그인 필요` 칸**에 적는다.
   - **메모에 한 줄 더 적을 것** — `카카오 또는 Apple 계정으로만
     로그인합니다. 아래 계정은 이미 승인되어 있습니다.` (영문으로도 함께)

(**4.2 최소 기능**은 이제 안 걸린다 — 네이티브 글칸과 푸시가 붙어 있다.
다만 **푸시는 `.p8` 열쇠를 넣어야 켜지므로**(`docs/설치.md` 7-1번) 그것부터
할 것.)

### 사용자가 컴퓨터에서 할 일 — 순서대로

**전부 <https://appstoreconnect.apple.com> 한 곳에서 한다.**
아이폰으로도 되지만 스크린샷을 올리고 설명을 적는 일이라 **컴퓨터가 훨씬 빠르다.**

1. **앱 만들기** — `앱` → `+` → `신규 앱`
   - 플랫폼 `iOS` · 이름 **`까꿍데이`** · 기본 언어 `한국어`
   - 번들 ID는 목록에서 **`com.kkakkung.app`**을 고른다(TestFlight를 쓰고
     있으니 이미 있다)
   - SKU는 아무 글자나(`kkakkung`)
2. **빌드 고르기** — `앱 버전` 화면 아래 `빌드`에서 TestFlight에 올라간
   판 하나를 고른다. **새로 빌드할 필요가 없다.**
3. **스크린샷** — **6.9인치(1320×2868 또는 1290×2796) 한 벌이 필수다.**
   폰에서 찍어 옮기면 되고 **2장 이상**이면 된다(홈·라운드 상세·대화 정도).
   아이패드용은 아이폰 전용 앱이라 **안 올려도 된다.**
4. **설명·키워드·카테고리** — 카테고리는 `스포츠`, 두 번째는 비워도 된다.
5. **주소 둘** — 아래를 그대로 붙여넣는다(둘 다 **필수**다).

   ```
   지원 URL              https://seongho1203-star.github.io/teetime/support.html
   개인정보 처리방침 URL  https://seongho1203-star.github.io/teetime/privacy.html
   ```
6. **앱 개인정보(App Privacy)** — 무엇을 모으는지 고르는 설문이다.
   우리 앱은 **이름(닉네임)·전화번호·사진·사용자 콘텐츠(대화)·식별자**를
   모으고 **광고 추적은 안 한다**(추적 항목은 전부 `아니오`).
7. **연령 등급** — 문항에 전부 `없음`이면 4+가 나온다.
8. **심사 정보** — 위 3번의 **데모 계정**과 메모를 여기 적는다.
9. **`심사를 위해 제출`** — 그 뒤는 기다리면 된다.

## 1. 알림음 — `까꿍` 소리

카톡처럼 앱 고유의 알림음을 내고 싶다는 요청이다.

**웹푸시로는 불가능하다.** `Notification`의 `sound`는 어느 브라우저도 구현하지
않았고, 서비스워커는 오디오를 재생할 수 없다. 네이티브로 감싸야 열린다.

- **안드로이드** — 소리 파일을 `android/app/src/main/res/raw/`에 넣고
  **알림 채널**에 물린다. FCM 보낼 때 그 `channel_id`를 지정한다.
  - **소리는 채널에 박힌다.** 앱을 깐 뒤에 바꾸면 기존 사용자에게는 안 바뀌고,
    채널 id를 새로 만들어야 반영된다 → **출시 전에 확정할 것.**
  - 파일 이름은 **소문자·공백 없이**(`kkakkung.wav`). 아니면 못 읽는다.
- **iOS** — 파일을 앱 번들에 넣고 APNs payload에 `"sound": "kkakkung.caf"`.
  **30초를 넘으면 기본음으로 돌아간다.**

**준비물** — 1초 안팎의 소리 파일 하나. **직접 만든 것이어야 한다**(카톡 소리를
그대로 쓰면 남의 저작물이라 스토어에서 걸린다). wav로 받아서 안드로이드용과
iOS용(`.caf`)으로 변환한다.

### 1-1. 앱을 보고 있을 때 소리가 두 번 나던 것

아이폰 홈 화면 앱에서 **폰 기본 알림음과 `까꿍`이 같이 울렸다.** 알림은
서비스워커가 띄우고(폰 소리), 같은 순간 앱이 실시간 이벤트를 받아 `까꿍`을
내기 때문이다.

웹에서는 **보고 있을 때 알림을 소리 없이 띄우는 것**으로 막아 두었다
(`sw.js`의 `options.silent = seen`).

**실기기로 확인한 결과 — 반만 통한다:**

| | `silent` | 지금 나는 소리 |
|---|---|---|
| 안드로이드 | **지켜 준다** | `까꿍`만 ✅ |
| 아이폰 (홈 화면 앱) | **무시한다** | 폰 기본음 + `까꿍` ❌ |

**아이폰은 웹에서 더 팔 자리가 없다.** `silent`를 무시하는 것은 사파리
쪽이라 우리가 넘을 수 있는 벽이 아니다. `sw.js`의 처리는 안드로이드에서
값을 하므로 **그대로 두고**, 아이폰은 아래 네이티브 작업으로 없앤다.

(웹에서 굳이 맞추려면 *아이폰에서만 `까꿍`을 끄는* 길이 있다 — 소리는
하나가 되지만 폰 기본음만 남아 `까꿍`을 못 듣는다. 그래서 안 했다.)

**네이티브에서는 확실히 없앨 수 있다.** 앱이 앞에 떠 있을 때 알림을 어떻게
보여 줄지 앱이 정하기 때문이다.

- **iOS** — `UNUserNotificationCenterDelegate`의
  `willPresentNotification`에서 소리를 뺀 표시 옵션만 돌려준다
  (`[.banner, .badge]` — `.sound`를 빼면 된다).
- **안드로이드** — 앱이 앞에 있을 때는 알림을 아예 안 띄우고 앱이 직접
  소리를 내면 된다.

그때는 `sw.js`의 `silent` 처리도 함께 정리할지 판단할 것 (웹으로도 계속
쓸 거면 남겨 둔다).

## 2. 채팅창 오동작 — iOS 키보드가 화면을 미는 것 ✅ **끝났다**

> **실기기에서 확인됐다**(사용자 — `메시지입력창을 잡고 위로 올릴때 밀리는
> 증상은 없어졌어`). `@capacitor/keyboard`의 `resize: 'native'` 한 줄이
> 답이었고, 웹으로 넉 대를 헛짚었던 그 자리가 그것으로 끝났다.
>
> **다만 키보드에 맞춰 화면을 움직이는 일은 앱에서도 우리 몫이었다.**
> 아래 `감쌀 때 함께 볼 것`이 예고한 그대로 웹용 보정이 방해가 됐고
> (키보드가 먼저 뜨고 대화창이 뒤따라 뜨는 두 단계), 그걸 끄고 웹뷰에
> 맡겼더니 **이번엔 웹뷰가 엇박자로 움직였다**(`내려갈 때도 뭔가 엇박자야`).
>
> **원인은 플러그인의 타이밍이다.** `Keyboard.m`에 그대로 적혀 있다 —
> 열 때는 `키보드 애니메이션 시간 + 0.2초` **뒤에** 창을 줄이고, 닫을 때는
> `0.01초` 만에 늘린다. 키보드는 0.25초에 걸쳐 움직이는데 창은 0.45초 뒤에
> 툭 줄고, 내릴 때는 창이 먼저 늘어난다.
>
> 그래서 **플러그인이 창을 줄이기 전까지의 틈을 우리가 메운다** —
> `keyboardWillShow`는 애니메이션이 **시작하는 그 순간** 오므로 그때 우리가
> 먼저 줄이고, 창이 줄어드는 순간 우리 몫이 0이 되어 이어진다.
> 자세한 셈은 `CLAUDE.md`의 '앱 껍데기' 꼭지와 `Chat.tsx`의
> `앱: 키보드와 같은 박자로` 주석에 있다.
>
> 아래는 그 판단의 근거로 남겨 둔다.

`CLAUDE.md`의 'iOS 키보드' 절에 자세히 적혀 있다. 키보드가 올라오면 보이는
화면(333)이 문서가 놓인 자리(707)보다 작고, 그 차이만큼 **iOS가 화면을 민다.**
그 손짓은 웹에 이벤트조차 오지 않아서 `touch-action` · `overflow:hidden` ·
`touchmove` 삼키기 · `transform` 따라가기 **넷 다 안 통했다.** 지금은 움직임이
멎고 120ms 뒤에 제자리로 돌려놓는 것이 전부다.

**이건 Capacitor로 감싸면 사라지는 문제다.** `@capacitor/keyboard`의
`resize: 'native'`가 웹뷰 자체를 줄여 주면 밀 틈이 아예 없어진다.

감쌀 때 함께 볼 것:

- `resize: 'native'`로 두고, 웹용으로 넣어 둔 보정(`--kb` · `--vvh` ·
  `locked` · 120ms 되돌리기)이 **앱에서는 오히려 방해가 되지 않는지** 확인한다.
  네이티브가 웹뷰를 줄이면 `visualViewport`와 `innerHeight`가 같이 줄어서
  우리 계산이 0을 물고 아무 일도 안 하게 될 가능성이 높다 — 그러면 그대로 두고,
  어긋나면 앱일 때만(`Capacitor.isNativePlatform()`) 건너뛴다.
- **웹으로 쓰는 사람이 남아 있는 동안에는 웹용 보정을 지우지 말 것.**

**키보드를 내렸을 때 대화가 어긋나 앉던 것도 같은 뿌리다**(`settleList`).
웹에서는 키보드가 내려가는 동안 화면 높이가 **여러 단계에 걸쳐** 바뀌고
그때마다 iOS가 굴린 자리를 제 나름대로 손봐서, 우리는 0.6초 동안 뒤따라가며
자리를 다시 앉히는 것 말고는 할 수 있는 것이 없다(그래서 두 번 어긋났다 —
한 번은 위에 붙고, 한 번은 아래가 잘렸다).
`resize: 'native'`면 웹뷰가 한 번에 줄었다 늘어나므로 이 뒤따라가기 자체가
필요 없어진다. **감쌀 때 `settleList`도 함께 볼 것** — 앱에서 남겨 두면
사람이 굴려 둔 자리를 앱만 아는 이유로 끌어내릴 수 있다.

### 2-1. 천지인 자판으로 칠 때 글씨가 깜빡이는 것 — **만들었다. 확인이 남았다**

> **앱에서 확인했다 — 예고한 대로 그대로다**(사용자 — `광칠때 깜빡이는거
> 증상 그대로나와`). 이로써 **웹뷰로 감싸는 것으로는 안 풀린다**는 것이
> 짐작이 아니라 확인된 사실이 됐다. 남은 길은 하나뿐이었다 —
> **입력칸만 네이티브로 바꾸는 것.** 그것을 만들었다.

> **지금 상태** — 사용자 요청(`댓글창이랑 채팅창 네이티브로 수정하자`)으로
> 네이티브 글칸을 넣었다. 파일은 셋이다:
> `ios/App/App/ComposerBar.swift`(바) ·
> `ios/App/App/NativeComposerPlugin.swift`(다리) ·
> `src/lib/composer.ts`(웹 쪽). 대화와 댓글이 **같은 바**를 쓴다.
>
> **아직 폰에서 확인하지 못했다.** 여기에는 맥도 아이폰도 없어서 Swift는
> **GitHub의 맥이 컴파일해 주는 것까지만** 확인된다 — 실제로 어떻게
>움직이는지는 TestFlight로 받아 봐야 안다. 그래서 **손볼 만한 값은 전부
> 웹 쪽(`composerSkin()`)에 두었다**: 크기·색·탭바 자리·단추 유무가 다
> 거기서 간다. 어긋나면 앱을 다시 안 만들고 밀기만 하면 된다.
>
> **되물러남이 걸려 있다.** 플러그인이 없는 판(지금 폰에 깔린 앱)에서는
> `ready()`가 던지고 **예전 웹 글칸이 그대로 쓰인다** — 웹을 먼저 밀어도
> 아무것도 안 깨진다. 통째로 끄는 스위치도 웹에 있다(`teetime:nc`).

**웹으로는 못 고친다. 감싸는 것만으로도 안 없어진다.** 위 2번과 달리
`@capacitor/keyboard` 같은 설정으로 풀리는 문제가 아니라, **입력칸 자체를
네이티브로 바꿔야** 사라진다.

원인은 `CLAUDE.md`의 `깜빡임의 진짜 원인` 꼭지에 자세히 있다 — 아이폰
천지인은 웹 글칸에서 조합을 안 쓰고, 글자를 바꿀 때 **칸을 7~13ms 동안
진짜 비웠다가 다시 채운다.** 그 사이에 화면이 그려지면 글씨가 사라졌다
나온다. 폰에서 여섯 가지 칸으로 갈라 봤고(맨 칸·자동수정 끔·`input`·
`contenteditable` 포함) **전부 똑같았다.**

**이 일이 값이 두 배가 됐다 — 키보드 부드러움도 같은 자리에서 풀린다.**
사용자가 `카카오톡은 엄청 부드럽게 되는데 이거는 왜 그렇게 못 만들어?`라고
물었고, 답은 **카톡의 입력칸이 키보드에 붙어 있는 네이티브 뷰**
(`inputAccessoryView`)라는 것이다 — iOS가 키보드와 그 칸을 **한 번의
움직임으로 함께** 옮기므로 맞출 것이 애초에 없다. 우리는 iOS의 키보드 ·
플러그인이 줄이는 웹뷰 · 그 안의 웹 화면 **셋이 따로 놀고**, 화면은 키보드가
움직이기 시작한 **뒤에야** 그 사실을 전해 듣는다(2번 꼭지의 보정들은 그 틈을
좁히는 것이지 없애는 것이 아니다).

**즉 남은 아이폰 문제 둘(깜빡임 · 키보드 부드러움)이 고칠 자리가 하나다.**
할지 말지를 정할 때 이 둘을 함께 놓고 볼 것.

**어떻게 만들었나 — 화면 아래에 늘 서 있는 보통 뷰를 `keyboardLayoutGuide`에
묶었다.** 키보드가 오르내리면 iOS가 그 안내선을 키보드와 같은 움직임으로
옮기므로 바가 붙어서 함께 간다.

처음(1판)에는 카톡처럼 **`inputAccessoryView`** 로 만들었는데 실기기에서
갈렸다 — first responder가 곧 생명줄이라, **대화 바탕을 한 번 누르기만 해도
웹뷰가 그 자리를 가져가 바가 통째로 사라졌고**, 되받으면 탭바 밑에서 다시
솟아오르는 것이 보였다. 보통 뷰로 세우면 누가 first responder든 바는 그
자리에 있다(2판 — `ready()`의 `v`가 그 번호다).

- 바가 맡는 것은 **한 줄뿐이다**: `+` · 글칸 · 이모티콘 · 보내기.
  인용(답장) · 언급 목록 · 이모티콘 미리보기 · 서랍은 **그대로 웹이** 그
  위에 그린다. 바가 가리는 만큼만 비운다(`--composer`, 바가 알려 준다).
- 우리 앱은 화면 맨 아래가 **탭바** 자리라, 키보드가 내려가 있을 때는
  바 아래에 그 높이(`tabH`)만큼을 **칠하지도 손짓을 받지도 않고** 비운다 —
  밑에 있는 웹 탭바가 그대로 보이고 눌린다.
  **여기가 실기기에서 어긋날 만한 자리다.** 만약 탭바가 안 눌리면
  `composerSkin()`의 `tabH`를 0으로 주고 웹에서 탭바를 감추면 된다 —
  **웹만 밀면 되므로 앱을 다시 안 만들어도 된다.**
- 댓글은 대화와 둘이 다르다: 바가 **적는 동안만** 뜨고, `+`와 이모티콘
  단추가 없다. 덤으로 **`키보드가 댓글 칸을 가린다`가 아예 없어진다** —
  적는 자리가 키보드에 붙어 있으므로 가릴 것이 없다.

> **첫 빌드는 플러그인이 등록조차 안 돼 아무것도 안 바뀌었다**(사용자
> 확인 — `광 쓸 때 끊기는 거 똑같고 키보드하고 채팅창하고 따로 노는 느낌도
> 똑같아`). Capacitor 7은 `capacitor.config.json`의 `packageClassList`만
>읽고 런타임을 훑지 않아서, 앱 폴더에 넣어 둔 Swift는 영영 안 불린다.
> `ios/App/App/MainViewController.swift`가 손으로 등록하고
> `Main.storyboard`가 그 클래스를 가리키게 고쳤다.
> **`내 정보` 맨 아래 `글칸 앱O·플러그인O·바O`로 확인할 수 있다.**

**확인할 때 볼 것 (실기기):**

0. **`내 정보` 맨 아래 줄**이 `글칸 앱O·플러그인O·바O`인지. 하나라도 `X`면
   아래를 볼 것도 없다 — `플러그인X`면 새 판이 아직 안 깔린 것이고,
   `바X`면 세우려다 실패해 스스로 웹 글칸으로 되돌린 것이다.
1. `광`을 쳐 봐서 깜빡이는지 — 이게 이 일의 본전이다.
2. 키보드를 올리고 내릴 때 바가 **따로 놀지 않는지**.
3. 대화에서 키보드가 내려가 있을 때 **탭바가 보이고 눌리는지**.
   - 탭바가 **안 눌리면**: `composerSkin()`의 `tabH`를 0으로 주고
     대화 화면에서 탭바를 감춘다(웹만 밀면 된다).
   - 탭바를 **반쯤 덮으면**: 바가 홈 인디케이터 자리를 못 잰 것이다.
     `tabH`에 그 높이(`--safe-b`)만큼을 더 얹으면 맞는다(역시 웹만 밀면 된다).
4. `+`(사진) · 이모티콘 · 보내기가 예전처럼 도는지.
5. 댓글 칸을 누르면 바가 뜨고, 보내면 댓글이 달리는지.

- **그 전까지의 안내는 `쿼티 자판으로 치면 안 그렇다`가 전부다.** 쿼티는
  한 글자가 내내 한 글자라 지웠다 쓰는 길로 안 간다(저장소 주인이 두
  자판을 견줘 확인해 줬다).
- 안드로이드는 자판이 달라 이 증상이 없다.

## 3. 뱃지 숫자를 서버가 세게

지금은 **서비스워커가 센다** — 알림이 올 때마다 1씩 올리고 앱을 열면 0으로
지운다(`public/sw.js`의 `bumpBadge`, `src/lib/badge.ts`). 정확한 안 읽음
개수가 아니라 **"앱을 연 뒤로 온 알림 수"**라, 폰과 PC를 같이 쓰면 기기마다
숫자가 다르다.

**iOS 앱에서는 서버가 실어 보낼 수 있다** — APNs payload의 `badge`에 숫자를
넣으면 그 값이 그대로 찍힌다. 그러려면 발송기가 사람별 안 읽음 개수를 알아야
하는데, 지금 안 읽음은 기기 안에서만(`teetime:seen:`) 센다. 서버가 세게 하려면
읽음 표시를 DB로 올려야 하니 **그만한 값이 있는지 먼저 재 볼 것.**

**안드로이드는 감싸도 그대로다.** 뱃지 숫자 표준이 없어 런처가 정한다
(삼성은 숫자, 순정은 점만). 이건 안드로이드 자체의 한계다.

## 4. 알림을 누르면 그 화면으로 — 앱에서 확실히

정산을 누르면 그 라운드, 대화를 누르면 대화방으로 가야 한다.

**웹에서는 이미 해 두었지만 아이폰이 미덥지 않다.** 앱이 꺼져 있을 때
`clients.openWindow(주소)`를 아이폰이 **무시하고 첫 화면으로 띄우기도 한다.**
그래서 `sw.js`가 갈 곳을 IndexedDB에 적어 두고 앱이 켜질 때 가져가는
예비 길(`putNav` / `take-nav`)까지 깔았다. 그래도 안 되면 이 항목으로 넘어온다.

**네이티브에서는 확실히 된다.** 알림을 누른 사건을 앱이 직접 받기 때문이다.

**고칠 것이 거의 없다는 게 요점이다** — 갈 곳(`url`)은 발송기가 이미
알림마다 실어 보내고 있고(`planFor`의 `url`), 옮기는 함수도 이미 있다
(`lib/push.ts`의 `goTo` — 해시만 갈아 끼운다). **둘을 이어 주기만 하면 된다.**

```ts
import { PushNotifications } from '@capacitor/push-notifications';

// 알림을 눌렀을 때. 앱이 꺼져 있다 켜지는 경우도 이 사건으로 들어온다.
PushNotifications.addListener('pushNotificationActionPerformed', e => {
    const url = e.notification.data?.url;      // 예: '#/rounds/{id}'
    if (url) goTo(url);                        // lib/push.ts 의 그 함수
});
```

**주의할 것 둘:**

- **`url`은 반드시 `data`에 실어야 한다.** FCM의 `notification` 블록에 넣으면
  앱이 꺼져 있을 때 시스템이 알림만 띄우고 그 값을 안 넘겨준다. 지금
  발송기는 `{title, body, tag, url}`을 한 덩어리로 보내므로, FCM으로
  바꿀 때 **`url`이 `data` 쪽에 남게** 할 것.
- **앱이 꺼져 있다 켜지는 경우, 화면이 준비되기 전에 사건이 먼저 올 수 있다.**
  그때는 `goTo`가 아직 없는 화면으로 보내는 셈이라, 웹에서 쓴 것과 같은
  방식으로 **한 번 적어 두었다가 앱이 준비되면 옮기는** 편이 안전하다.

## 함께 정해 둔 것들 (감쌀 때 필요)

- **Capacitor 하나로 안드로이드·iOS 둘 다.** iOS에는 TWA가 없고, 섞으면
  알림이 두 벌이 된다.
- **알림을 FCM으로 통일한다.** iOS 웹뷰에서는 웹푸시가 안 돈다.
  - **누구에게 보낼지 정하는 부분(`planFor` · `@전체` · 대화 스위치)은 그대로 둔다.**
    바뀌는 것은 미는 방법뿐이다 — `push.ts` · `sw.js` · `push_subscriptions`
    (구독 대신 토큰) · `notify`의 발송 한 토막.
  - 전환 기간에는 웹으로 쓰는 사람과 앱으로 옮긴 사람이 섞이므로
    `push_subscriptions`에 `kind`(웹/앱) 칸을 두고 **둘 다 보낸다.**
    다 옮긴 뒤에 웹 쪽을 걷어낸다.
- **카카오 로그인 딥링크.** 앱 안에서 로그인하고 앱으로 돌아오려면 커스텀 스킴을
  카카오와 Supabase Auth 양쪽의 redirect URL에 등록해야 한다. 제일 잘 막히는 자리다.
- **패키지 이름은 한 번 정하면 못 바꾼다** (`com.kkakkung.app` 예정).
- **서명 키는 잃어버리면 앱을 영영 갱신 못 한다.** 만들고 바로 백업하고,
  **Play 앱 서명**을 켜서 구글에도 맡겨 둘 것(위 0번 표).
- **개인정보처리방침 URL**이 없으면 플레이 콘솔에서 반려된다.
- 해시 라우팅과 `vite.config.ts`의 `base: './'`은 **이걸 위해 그렇게 해 둔 것**이다.
  건드리지 말 것.
